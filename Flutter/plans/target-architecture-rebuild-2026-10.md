## 迁移批次

### 0. 可重复的工程基线

修复已确认的 UI/外观 fixture 与原生通道清理问题；固定 SDK 和离线验证
入口；外部服务/真机测试与 PR gate 分离。保存改动前结果，区分已确认失败
与不稳定测试。不为获得绿灯跳过断言或提高阈值。

验收：相关套件可重复；CI 入口不隐式访问生产；失败可定位并有明确归属。

### 1. 一个真实垂直切片验证目标结构

选择支付能力作为首个切片：已有独立协议 Client、控制器和装配，测试可以
模拟交易结果。先修复该能力旧断言，明确应用接口、界面状态与适配器所有权，
去掉界面对全局装配的依赖。复用现有算法和协议行为，不顺带重写支付流程。
验证流订阅释放、账户切换和服务端确认前不完成交易等约束。

验收：业务对象无需 Flutter/Riverpod/全局容器即可测试；应用层不依赖具体
适配器；相同输入的状态和请求语义与迁移前一致。无真实支付调用。

### 2. API 统一治理

按实际服务核对后端实现、协议、认证受众和环境配置。将域 Client 与 wire
模型按业务拆分，清理宽泛兼容出口。建立网络客户端创建边界、脱敏诊断及
域内契约测试。上传、下载、SSE、声纹作为显式专用通道接入公共治理。
先统一机制与归属，再逐项决定认证行为是否需要调整，不能一刀切复用 Token。

验收：普通业务模块不直接创建 Transport；页面不拼请求/认证头；端点定义
有唯一运行时来源；超时、取消、幂等、刷新和账号切换场景有测试。服务端
兼容性需要独立证据，静态一致性不能代替联调。

### 3. 业务模块及双端应用壳

按真实依赖拆 ui_v3，优先定位/知识/创作，再拆桌面 editor_workspace 的
多业务状态；导航与布局归应用壳，跨模块流程归显式协调器。只有具备两个
真实消费者且行为一致时才提升共享业务代码。每个切片迁移消费者后删除旧入口。

验收：跨模块只依赖公开应用接口；页面无持久化/网络副作用；共享业务层
不依赖应用根或平台插件；移动/桌面语义通过合同测试验证。

### 4. 存储与设备专项

分别建立存储写入权威和录音设备连接/传输/账本边界。执行前补充数据版本
与协议评审；写入失败、进程终止、账号切换、迟到回调和断点恢复有专项测试。
保留兼容迁移直到退出条件满足，硬件变化以真机回归验收。

### 5. 收尾与删除

业务边界稳定后独立整理 apps 路径、包名与构建脚本。删除无消费者的兼容
出口和旧路径，收紧迁移例外。不得只重命名目录便宣称架构完成。

## 每批共同准入与退出条件

实施前写清目标符号、输入输出、消费者、共享/原生边界及回滚方式。
格式、分析、聚焦行为测试、依赖影响复查通过后才进入下一切片。回滚限定
当前批次；数据格式改变时必须另有兼容和恢复方案。线上/服务器只读。
