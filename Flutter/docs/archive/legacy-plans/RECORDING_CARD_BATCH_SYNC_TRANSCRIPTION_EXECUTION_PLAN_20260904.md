## 一、方案目标

本次重构解决四类当前混合在一起的问题：

1. 录音卡设备管理页同时展示本地文件和卡内文件，数据归属不清楚。
2. 批量管理入口、选择状态和批量动作没有形成完整且稳定的状态机。
3. 当前列表页面一次只允许发起一个转写，无法表达一个批次内多个文件的独立进度。
4. 当前自动同步主要依赖“设备仍报告为未同步”和临时任务记录，用户主动删除本地文件后可能再次自动同步。

目标结果：

- 本地录音页只展示已经同步到本地且本地文件仍然有效的录音。
- 卡内文件只在录音卡详情下的独立页面展示。
- 本地页批量动作只提供“删除本地”和“转写”。
- 卡内文件页批量动作只提供“同步到本地”和“删除卡内文件”。
- 冻结选择快照只有 1 个文件时沿用单文件转写；选择 2 个及以上文件时才创建批量转写批次。一个批次只有一条聚合处理中消息，但每个文件可以独立产生完成、失败和纲要结果消息。
- 每个文件具有持久的文件级同步记录和转写记录，并可显示文件名、时间和标签。
- 用户主动删除本地文件后不会自动回流；用户在卡内文件页主动同步该文件时，可以恢复为“已同步”。
- 账号切换、录音卡解绑、绑定其他录音卡和重新绑定旧录音卡时，账本严格隔离且不会被误清除。

## 二、已确认的产品规则

### 2.1 页面和删除边界

- 本地录音页只负责本地文件。
- 本地录音页的删除只删除本地文件，不再提供“删除卡内文件”或“同时删除两处”。
- 卡内文件页只负责录音卡内的文件；删除动作只删除录音卡文件。
- 删除本地文件或卡内文件均不删除已经生成的云端录音、资产、转写正文或纲要。
- 如果一个本地文件正在上传，暂时禁止删除该本地文件；已经被后端接受的转写不因用户离开页面而停止。

### 2.2 同步边界

- 某账号首次连接某张录音卡时，默认自动同步当前卡内的全部文件。
- 后续连接优先恢复上次未完成的文件，再处理新发现的文件。
- 只有本轮冻结的候选文件全部完成并通过本地校验，才允许提交新的自动同步水位。
- 中途断连、录音卡开始录音、用户暂停、权限失败、空间不足或传输失败时，不提交本轮水位。
- 已经完成的单文件结果立即写入文件账本；下次连接时不重复传输。
- 用户主动删除本地文件后，文件账本更新为“本地已删除”，自动同步不得重新下载。
- 用户在卡内文件页对“本地已删除”的文件主动执行同步后，状态重新变为“已同步”。
- 解绑录音卡不删除这张卡的历史账本；同一账号重新绑定时继续使用。
- App 正常升级不得删除或覆盖账本；卸载 App 后随应用数据一起删除是允许的边界。

### 2.3 转写和通知边界

- 批量转写中的文件共享一条聚合消息和一个批次中间页。
- 以用户点击“转写”时冻结的选择数量作为唯一分流边界：`0` 个时按钮禁用，`1` 个时进入现有单文件链路，`>= 2` 个时进入多文件批次链路。后续分类出已转写或不可用文件时不改变本次分流，避免确认前后页面跳变。
- 聚合消息按批次实时显示总数、处理中、已完成、失败和超时数量。
- 聚合消息点击后进入批次中间页，而不是随机进入某一个文件详情。
- “转写完成”和“资产已生成”合并为一条单文件“转写完成”通知，只有最终转写存在且资产可访问时生成；纲要完成、失败或超时仍可以单独产生通知。
- 已经完成转写的文件不重复提交。
- 已经存在远端录音或正在处理的文件加入当前批次观察，不创建第二个远端录音。
- 批次中的每个文件独立完成、失败、超时和重试，单个文件不能阻断其他文件。
- 批次在仍有非终态文件时保持“处理中”；所有文件进入终态后才结束处理中状态。
- 纲要是转写后的独立派生结果，不阻塞“批量转写已结束”的判定。

## 四、目标信息架构

| 页面 | 数据所有者 | 展示内容 | 批量动作 |
|---|---|---|---|
| `/v3/recording-card` | 本地录音库 | 已同步且本地文件有效的录音 | 删除本地、转写 |
| `/v3/recording-card/details` | 录音卡设备状态与同步摘要 | 设备信息、卡内统计、最近同步 | 进入卡内文件页 |
| `/v3/recording-card/files` | 当前录音卡文件目录与文件账本 | 卡内文件、上次读取缓存、同步/转写标签 | 同步到本地、删除卡内文件 |
| `/v3/feed/transcription-batches/:batchId` | 批量转写控制器 | 聚合进度、逐文件状态、失败重试 | 返回后台、重试单项、查看结果 |

### 4.1 本地录音页

普通状态标题行：

```text
录音文件                                      批量管理
```

批量状态标题行：

```text
已选择 N 条                         全选  清除  退出
```

底部动作：

```text
删除本地                                      转写
```

规则：

- “全选”锁存当前页面当前筛选结果，不自动包含之后新增的文件。
- “清除”只清空选择，不退出批量模式。
- “退出”和系统返回键都清空选择并退出批量模式。
- 普通状态点击录音仍执行原有播放或详情操作。
- 批量状态点击整行只切换选中状态，不打开播放器或详情。
- 拖动滚动条、滚动列表和播放器进度条不能误触发选择。
- 每条录音保留文件名；录音卡来源的有效本地文件显示 `已同步`，存在转写凭据时同时显示 `已转写`。
- 底部动作没有选择项时禁用；动作开始时使用不可变的选择快照。
- 删除成功的行立即从本地列表移除；失败项保留选中以便重试。

### 4.2 卡内文件页

入口位于录音卡详情的“录音卡存储”区域，整块区域可点击并显示右箭头。

页面沿用当前录音卡设备管理页的 V3 视觉和交互组件：使用原有页面间距、标题层级、`V3Card`、底部操作面板、带图标的 `ListTile` 操作项和批量底栏，不另造一套样式。

普通状态标题行：

```text
卡内录音（N）                                 批量管理
```

批量状态标题行：

```text
已选择 N 条                         全选  清除  退出
```

交互规则与本地录音页一致：全选锁存当前可选快照，清除只清空选择，退出和系统返回键清空选择并退出；批量状态点击整行只切换选中，滚动和拖动不能误选。没有选择项时底部动作禁用，动作开始后使用不可变选择快照。

当前本地文件列表三点菜单中的设备文件能力迁移到卡内文件页，不再从本地录音列表暴露。卡内文件页右上角保留“文件操作”三点入口，点击后复用现有底部操作面板样式，提供：

- `刷新文件列表`：重新读取当前卡目录；读取时显示行内加载状态，不清空上一次成功快照。
- `蓝牙传输`：进入批量选择并将待执行动作锁存为蓝牙同步。
- `Wi-Fi 传输`：进入批量选择并将待执行动作锁存为 Wi-Fi 同步；能力不可用时禁用并显示原因。
- `删除录音卡文件`：进入批量选择并将待执行动作锁存为卡内删除。

直接点击标题行“批量管理”时不预设动作，底部同时显示“同步到本地”和“删除卡内文件”。点击“同步到本地”后再选择蓝牙或 Wi-Fi；从三点菜单进入时底栏突出对应动作，但用户仍可退出后重新选择，不能静默执行。

页面默认按录音日期分组、组内按时间从新到旧排列。一次同步结束后，页面摘要显示本轮完成数量以及这些录音的最早和最晚录音时间；无法确定时间的文件单独归入“时间未知”。每一行至少显示：

- 文件名。
- 录音时间；时间不能解析时显示“时间未知”。
- 文件大小和时长；设备未提供时不伪造。
- 最近一次同步完成时间；从未同步时不显示伪时间。
- 本地状态标签：`未同步`、`同步中`、`已同步`、`本地已删除`、`同步失败`。
- 转写标签：仅在确有本地转写完成凭据时显示 `已转写`。

批量状态底部只显示：

- `同步到本地`：点击后选择“蓝牙传输”或“Wi-Fi 快速传输”；能力不可用时禁用对应方式并展示原因。
- `删除卡内文件`：破坏性动作，必须显示选中数量并二次确认。

卡内文件页不直接增加第三个“转写”底栏按钮。文件必须先成为有效本地录音，再由本地录音页发起批量转写；如果“同步后自动转写”设置开启，则继续复用现有自动转写链路。

离线状态：

- 如果有账本缓存，展示“上次读取”的文件列表，所有设备写操作禁用。
- 如果没有缓存，展示连接录音卡操作，不展示伪造文件。
- 单次扫描缺少某文件不能直接判定该文件已从卡内删除；只有明确的删除成功回执才能写入“卡内已删除”。
- 离线页不调用设备目录扫描；只展示“显示上次读取结果”和“连接录音卡”入口。重新连接成功后由连接修订触发读取，不能把离线或失败刷新投影为空列表。
- 空列表只在当前连接、当前 SN 的目录读取成功且确认为零文件时显示；读取失败、权限不足和设备忙分别显示可恢复错误状态。

### 4.3 设备详情页

“录音卡存储”增加：

- 卡内录音数量。
- 已同步到本地数量。
- 本地已删除但卡内仍存在数量。
- 待同步数量。
- 最近成功同步时间。
- 最近读取卡内目录时间。

“最近成功同步时间”和“最近读取时间”必须分开：读取目录但没有传输文件时，不得伪装为完成了一次同步。

## 五、稳定身份和账号隔离

### 5.1 录音卡身份

永久账本键使用：

```text
accountScope + sha256(normalizedSerialNumber)
```

产品语义上每个账号拥有一份独立账本，账本内再按录音卡 SN 摘要分区。物理实现继续使用现有持久 `AppDatabase` 和 `user_scope` 隔离，不为每个账号维护容易损坏或覆盖的独立 JSON 文件。

规则：

- 不在账本中保存明文 SN。
- `safeDeviceFingerprint` 只用于当前 BLE 连接和短期传输恢复，不作为永久同步水位主键。
- 同一账号连接新录音卡时创建新的卡账本，不覆盖旧卡账本。
- 同一账号重新连接旧录音卡时加载旧卡账本。
- 不同账号即使连接同一张卡，也不能读取彼此的本地账本。
- 解绑只结束当前绑定关系，不清除账号下该 SN 摘要对应的账本。

### 5.2 文件身份

卡内文件在下载前的源签名：

```text
sha256(cardSnDigest + deviceFileId + deviceFilename + sizeBytes + recordedAt)
```

下载并完成本地校验后增加 `contentHash`。判断顺序：

1. 有可信 `contentHash` 时优先按内容哈希确认同一文件。
2. 下载前使用卡 SN 摘要和源签名。
3. 设备复用了 `deviceFileId` 但文件名、大小或时间变化时，视为新文件。
4. 如果设备同时复用了全部元数据且未提供内容哈希，客户端无法在下载前证明是新内容；此限制必须保留在诊断日志中，不进行猜测。

## 六、本地持久化模型

不新增独立的松散 JSON 缓存。账本存入现有账号隔离 `AppDatabase`，使用加法式 schema 迁移，正常升级只新增结构，不清空旧表。

### 6.1 `recording_card_file_ledger`

每个卡内源文件一条记录，关键字段：

| 字段 | 说明 |
|---|---|
| `user_scope` | 账号隔离 |
| `card_sn_digest` | 规范化 SN 的 SHA-256 |
| `source_signature` | 卡内源文件稳定签名 |
| `device_file_id` | 设备文件标识 |
| `device_filename` | 用于文件级展示，不得缺失 |
| `recorded_at` | 设备时间或文件名推导时间，可为空 |
| `size_bytes`、`duration_seconds` | 客观文件元数据，可为空 |
| `content_hash` | 下载校验后写入 |
| `local_recording_id` | 当前关联的本地录音，可为空 |
| `local_state` | 本地同步状态 |
| `card_state` | 卡内存在状态 |
| `last_synced_at` | 该文件最近一次校验完成时间 |
| `local_deleted_at` | 用户主动删除本地文件时间 |
| `last_seen_at` | 最近一次在卡内目录看到的时间 |
| `error_code` | 最近一次同步错误，可为空 |
| `retryability` | `transient` 或 `permanent`；仅失败时有值 |
| `attempt_count`、`next_retry_at` | 自动重试次数和下一次允许重试时间 |
| `updated_at` | 账本更新时间 |

`local_state` 保留必要状态：

| 状态 | 含义 | 允许的后继状态 |
|---|---|---|
| `neverSynced` | 已发现但从未同步 | `queued` |
| `legacyUnknown` | 升级迁移时无法证明是否同步过的历史文件 | 仅用户手动同步可转为 `queued` |
| `queued` | 已进入本次同步计划，或中断后等待恢复 | `syncing`、`failed` |
| `syncing` | 正在传输或校验 | `synced`、`failed`；断连、进程退出或账号作用域卸载时回到 `queued` |
| `synced` | 本地文件、记录和校验凭据均有效 | `deleting`、`queued` |
| `deleting` | 正在执行本地删除 | `localDeleted`、`synced` |
| `localDeleted` | 用户明确删除本地文件 | 仅手动同步可转为 `queued` |
| `failed` | 收到明确传输错误 | `transient` 可在下一个合格触发事件自动转为 `queued`；`permanent` 仅显式重试可转为 `queued` |

`card_state` 与 `local_state` 正交，避免组合出大量状态：

- `present`：最近确认在卡内。
- `deleted`：收到明确的卡内删除成功回执。
- `unknown`：离线或当前扫描无法证明是否仍存在。

### 6.2 `recording_card_sync_checkpoints`

每个 `user_scope + card_sn_digest` 一条记录：

| 字段 | 说明 |
|---|---|
| `last_successful_auto_sync_at` | 最近一次完整自动同步提交时间 |
| `last_transfer_completed_at` | 最近一次自动或手动文件传输完成时间 |
| `last_directory_read_at` | 最近一次成功读取卡内目录时间 |
| `committed_through_recorded_at` | 已提交快照中的最大有效设备录音时间 |
| `committed_snapshot_hash` | 已提交目录快照签名 |
| `migration_mode` | 新设备、旧数据迁移或正常状态 |
| `updated_at` | 更新时间 |

时间水位只用于快速筛选和展示，文件账本才是去重与防回流事实。`recordedAt` 为空、回拨或早于水位，但源签名从未出现的文件仍作为新文件处理。

### 6.3 `recording_transcription_receipts`

每个已处理本地音频一条记录：

| 字段 | 说明 |
|---|---|
| `user_scope` | 账号隔离 |
| `file_identity` | 优先为内容哈希，卡文件可关联源签名 |
| `device_filename` | 卡文件原始文件名，可为空 |
| `content_hash` | 已校验音频哈希 |
| `local_recording_id` | 当前本地录音 ID，可为空 |
| `remote_recording_id` | 后端录音 ID |
| `note_id` | 已生成的云端资产 ID，可为空 |
| `transcript_completed_at` | 后端确认最终转写的时间 |
| `asset_ready_at` | 云端资产可访问时间，可为空 |
| `outline_completed_at` | 纲要完成时间，可为空 |
| `updated_at` | 更新时间 |

写入规则：

- 创建请求成功、上传成功或 ASR 入队都不能写“已转写”。
- 只有后端详情出现最终转写事实时才写 `transcript_completed_at`。
- 云端资产准备好后补写 `note_id` 和 `asset_ready_at`。
- 纲要完成后补写 `outline_completed_at`。
- 本地录音页和卡内文件页的“已转写”标签只读取 `transcript_completed_at`。
- 删除本地文件、删除卡内文件或解绑录音卡都不删除转写凭据。
- 老版本文件不进行全库补标；但已有 `remoteRecordingId` 的文件在重新操作时必须先观察原任务，不能重复创建远端录音。
- 对旧文件只做按需核验：用户再次操作或页面需要展示状态时查询原 `remoteRecordingId`。后端确认最终转写后补写本地凭据；查询失败或离线时保持“待核验”，不得据此创建新远端录音，也不启动全库回填。

### 6.4 批量转写批次记录

复用 `local_transfer_records` 保存批次清单，`transfer_kind` 使用新的明确值，例如 `recording_batch_transcription`。批次至少持久化：

- `batch_id`。
- 创建账号和工作区作用域。
- 创建时间和更新时间。
- `primary_item_id`。
- 每个文件的顺序、文件身份、本地录音 ID、`jobId`、远端录音 ID。
- 当前批次状态、单文件状态、最近阶段、尝试次数、错误码和超时事实。
- 远端观察的 `observation_started_at`、`last_authoritative_progress_at`、`observation_deadline_at` 和等待原因；App 重启不得重置截止时间。

活动批次不得被普通本地文件元数据清理逻辑提前删除。批次全部终结且没有消息、恢复或重试引用后，才按照现有消息保留策略压缩；文件同步账本和转写凭据不随批次压缩。

## 七、批量选择状态机

批量选择只需要两个持久 UI 状态和一个短期动作状态：

| 状态 | 进入条件 | 行为 | 退出条件 |
|---|---|---|---|
| `inactive` | 页面初始或退出批量管理 | 普通点击、播放和详情 | 点击“批量管理” |
| `selecting` | 点击“批量管理” | 行点击切换选择，显示三个顶部按钮和底部动作 | 退出、返回或动作接受 |
| `executing` | 删除执行或创建转写批次 | 冻结选择快照，禁止重复提交 | 删除结束或批次持久化完成 |

锁存规则：

- 选择键使用稳定文件身份，不使用列表索引。
- 数据刷新后只移除已不存在或已不具备操作资格的选择，不自动新增选择。
- “全选”保存当时的可选身份集合；同步进来的新文件不进入该集合。
- 删除期间退出页面不取消已经接受的删除操作。
- 转写批次持久化成功后退出选择模式并进入批次中间页。
- 批次持久化失败时保留原选择，用户可以重试。
- 删除或同步全部成功后退出选择模式；部分失败时回到 `selecting`，只保留失败项，已经成功的项不得再次执行。
- 账号切换、设备断连或 A 卡直接切换为 B 卡时，立即清空设备文件选择和预设动作；本地文件选择只受账号和本地列表有效性约束。

## 八、批量转写状态机

### 8.0 单文件与多文件分流

分流发生在冻结选择快照之后、逐项分类之前，边界不随分类结果变化：

| 冻结选择数 | 处理方式 | 页面与消息 |
|---|---|---|
| `0` | 不接受动作 | “转写”禁用，不创建任务 |
| `1` | 复用现有单文件上传、转写详情和通知链路 | 不创建 `batchId`，不显示聚合消息 |
| `>= 2` | 使用多文件编排并逐项分类；至少一项可执行或可观察时才创建活动批次 | 进入批次中间页，只生成一条聚合处理中消息；全为跳过/不可用时只显示分类结果，不伪造处理中状态 |

例如选择 2 个文件，其中 1 个已转写，仍属于多文件批次：已转写项显示 `skipped`，另一项继续处理。选择 2 个文件但全部已转写时，仍使用多文件确认结果，只是不创建活动任务和聚合处理中消息。这样用户从点击动作起就能获得稳定、可预测的页面和返回路径。

同一冻结预览只允许被消费一次。转写按钮在创建操作开始后立即锁存；快速双击、并发回调或重复路由提交必须共享同一个创建结果，不能生成两个 `batchId`、两组远端录音或两条聚合消息。

### 8.1 提交前分类

用户点击“转写”后，对冻结的选择快照逐项分类；这套分类由单文件和多文件链路共同复用：

| 分类 | 判定 | 处理 |
|---|---|---|
| `eligible` | 本地文件有效、格式支持、没有已有任务或完成凭据 | 创建批次项并提交 |
| `alreadyCompleted` | 本地转写凭据已有最终转写时间且资产已可访问 | 跳过提交，显示“已转写” |
| `existingRemoteCompleted` | 没有本地凭据，但原 `remoteRecordingId` 的权威详情已经包含最终转写且资产可访问 | 按需补写凭据并作为 `skipped`，不创建新录音 |
| `alreadyProcessing` | 有上传草稿、远端录音或追踪任务且权威状态未终结；也包括转写已经完成但资产仍在写入 | 加入批次观察，不重复提交 ASR；转写已完成时直接展示 `storingAsset` |
| `awaitingVerification` | 已有 `remoteRecordingId`，但离线或服务暂不可用，无法确认其状态 | 以 `pending + remoteVerificationRequired` 等待核验，禁止提交新录音 |
| `retryExisting` | 已有远端录音且后端允许重试 | 使用原录音重试接口，不新建录音 |
| `unavailable` | 文件缺失、格式不支持或账号/工作区永久不可用 | 映射为 `failed(retryable: false, category: unavailable)`，记录明确原因，不提交 |

确认面板显示：选择总数、将开始转写数量、正在处理中数量、已转写跳过数量和不可用数量。没有可执行或可观察项目时不创建活动批次。

### 8.2 单文件状态

只保留业务上需要的七个状态：

| 状态 | 含义 | 允许的后继状态 |
|---|---|---|
| `pending` | 排队，或等待网络、远端核验、账号/工作区条件 | `submitting`、`processing`、`failed` |
| `submitting` | 哈希、上传和创建远端录音 | `pending`（中断恢复）、`processing`、`failed` |
| `processing` | 后端转写或资产写入 | `completed`、`failed`、`timedOut` |
| `completed` | 最终转写存在且资产可访问 | 终态 |
| `failed` | 收到明确失败事实；`unavailable` 作为不可重试错误分类保存在此状态 | 显式重试后回到 `pending` 或 `processing`；同一远端 ID 的迟到权威成功可转 `completed` |
| `timedOut` | 后端明确返回超时，或持久 24 小时观察期限到达且权威查询仍未终结 | 恢复观察后回到原状态；同一远端 ID 的迟到权威成功可转 `completed` |
| `skipped` | 已转写，无需再次提交 | 终态 |

`processing` 内部展示阶段不单独扩展为持久状态，而是从现有事实投影：

- `uploading`：准备或上传音频。
- `transcribing`：后端 ASR 正在处理。
- `storingAsset`：最终转写已存在，云端资产仍在写入。
- `assetReady`：资产已经可访问，即将进入 `completed`。

纲要状态单独投影为：`notStarted`、`generating`、`completed`、`failed`。纲要失败不把已经完成的转写改回失败。

### 8.3 超时和错误边界

采用主流异步转写服务共同遵循的长任务原则，而不是把客户端一次等待超时当作后端失败：Google Cloud 将批量识别建模为可查询的 Long-Running Operation，并明确说明等待超时不代表转写失败；AWS 以服务端 `COMPLETED` / `FAILED` 作为终态；Azure 支持完成回调和状态查询，并提示批量任务在高峰时可能需要最长约 24 小时完成。参考：[Google Cloud 超时说明](https://docs.cloud.google.com/speech-to-text/docs/troubleshooting)、[Google Cloud 异步识别](https://cloud.google.com/speech-to-text/docs/batch-recognize)、[AWS GetTranscriptionJob](https://docs.aws.amazon.com/transcribe/latest/APIReference/API_GetTranscriptionJob.html)、[Azure 批量转写结果](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/batch-transcription-get)。

据此确定本工程边界：

- 上传 HTTP 请求、哈希和本地文件读取继续使用现有短时技术超时；这些超时只结束当前请求，不推断远端 ASR 失败。
- 获得 `remoteRecordingId` 后进入长任务观察，统一使用 24 小时“需要关注”期限，替换当前 `RecordingProcessingTracker` 默认 12 小时的观察值，不再新增第二套页面计时器。
- `observation_started_at` 在首次获得远端录音 ID 时锁存，`observation_deadline_at = observation_started_at + 24h`；批次页关闭、App 进入后台或重启都不能重置。
- 网络断开时保存 `waitingReason = networkRequired`，不把无法查询写成 `failed` 或 `timedOut`。如果截止时间已经到达但仍离线，继续保持等待；恢复联网后必须先进行一次权威详情查询。
- 截止后权威查询仍返回非终态，才写本地 `timedOut`。它表示“等待过久、需要用户关注”，不代表后端停止，也不触发重复上传。
- 后端明确返回 ASR `timeout`、`failed`、`cancelled`、资产写入失败或权限错误时，立即按权威事实进入 `timedOut` 或 `failed`，无需等待本地截止时间。
- 上传客户端返回明确错误时进入 `failed`，保留稳定错误码和可重试标记；界面不直接展示底层异常文本。
- 已获得 `remoteRecordingId` 后重试只恢复观察，或使用后端原录音重试接口；每次服务端接受的新逻辑尝试可以锁存新的 24 小时截止时间，但禁止重新上传并创建第二条录音。
- `timedOut` 后仍接受 Push 或权威详情的迟到成功；收到成功事实时更新文件、批次和原消息，不创建第二条完成通知。

### 8.4 批次聚合状态

| 批次状态 | 判定 | 聚合消息行为 |
|---|---|---|
| `active` | 至少一项为 `pending`、`submitting` 或 `processing` | 保留一条处理中消息 |
| `completed` | 所有项目为 `completed` 或 `skipped` | 聚合消息转成功并离开处理中列表 |
| `completedWithIssues` | 已无活动项，但至少一项 `failed` 或 `timedOut`；不可用文件属于不可重试 `failed` | 聚合消息转“需要处理”，保留适用的重试入口 |

聚合计数按以下方式计算：

```text
总数 = 活动 + 已完成 + 已跳过 + 可重试失败 + 其他不可重试失败 + 超时 + 不可用
```

“不可用”是 `failed(retryable: false, category: unavailable)` 的展示子类；`其他不可重试失败` 是其余永久失败。两者都从失败中拆分，不能重复计数。

聚合消息示例：

- `5 个录音文件正在转写`。
- `5 个录音：2 个已完成，3 个处理中`。
- `5 个录音处理结束，4 个完成，1 个需要重试`。

聚合消息使用稳定 `batchId` 更新同一条消息，不能在每次进度变化时创建新消息。

### 8.5 中间页生命周期

- 创建批次成功后立即进入中间页。
- 页面顶部显示总进度和 `已处理终态 / 总数`；完成、跳过、失败和超时都推进进度，避免带问题的终态批次停在未满进度。
- 每一行显示文件名、当前阶段、结果状态和必要动作。
- 完成项标记“已完成”，继续保留在列表中，不因其他项目仍在处理而消失。
- 失败或超时项显示错误摘要和单项重试。
- 用户点击返回时任务进入后台，不取消批次。
- 只要批次仍为 `active`，聚合消息始终可重新进入该页面。
- 所有项目终结后，中间页转为批次结果页，不强制自动关闭或跳走。
- 批次仍为 `active` 时，即使首个文件已经完成，也只能在当前页展示“查看结果”入口，不得自动跳离中间页。
- 批次成功时聚合消息从“处理中”区域移除并更新为历史结果，批次结果仍可由相关单文件通知和消息历史访问。
- 批次有失败或超时时，聚合消息保留为需要处理，直到重试成功或用户明确完成处理。

### 8.6 首项结果展示与导航

- `primaryItem` 在批次创建时锁存为当前排序中的第一条可执行或已在处理的文件。
- `primaryItem` 的资产可访问后，在中间页顶部或对应行展示明确的“查看结果”动作，不自动打开资产，不抢占用户当前导航。
- 其他文件完成时只更新页面和通知，也不得自动导航。
- 所有项目终结后，批次结果页默认选中并展示 `primaryItem` 的结果摘要；完整资产仍由用户点击进入。
- `primaryItem` 失败或超时时不自动改选；结果页保持第一项位置，并同时允许用户打开其他已完成项，避免默认对象在后台变化。

## 九、两级消息模型

### 9.1 批次聚合消息

同一批次在处理期间只有一条聚合消息：

- 消息 ID 由 `batchId` 稳定生成。
- 消息标题和正文由批次计数投影。
- 点击进入 `/v3/feed/transcription-batches/:batchId`。
- 可通过 `focusItem` 查询参数定位指定文件，但聚合消息默认展示整个批次。
- 进度更新只更新正文，不反复把用户已经读过的聚合消息标为未读。
- 批次成功结束后，同一消息 ID 更新为一次“批量转写完成”历史消息并从“处理中”列表移除；终态更新可以标记一次未读，但不得新增第二条聚合消息。
- 批次存在失败或超时则转为需要处理，不静默消失。
- “完成处理”只关闭聚合消息的待处理提示，不修改任何单文件事实；之后迟到成功更新原消息和批次，不重新创建处理中消息。

### 9.2 单文件消息

单文件链路和多文件批次必须分开投影：冻结选择数为 1 时完全沿用现有单文件消息；冻结选择数大于等于 2 时不再生成逐文件“正在转写”消息，只在有独立价值的事实发生时生成：

- `转写完成`：最终转写存在且资产可访问；与“资产已生成”合并，只生成这一条通知。
- `纲要已生成`：沿用现有纲要结果消息，直接进入资产纲要页。
- `转写失败`：进入批次页定位失败项，并提供原任务重试。
- `转写超时`：进入批次页定位超时项，恢复观察而不是重复创建录音。
- `纲要失败`：沿用独立纲要失败消息，不改变转写完成标签。

点击边界：

- 多文件批次仍为 `active` 时，该批次所属的转写完成、失败和超时通知统一进入批次中间页，并通过 `focusItem` 定位文件；转写完成项可在页内再点击“查看结果”。
- 多文件批次已经终结时，转写完成通知直接进入对应资产，失败或超时通知进入批次结果页并定位文件。
- 同一条单文件通知使用稳定消息 ID；批次从 `active` 进入终态时只更新其点击目标，不复制一条新通知。
- 纲要完成通知始终进入该文件的纲要页，因为纲要不参与批次转写终态。
- 单文件链路的成功、失败和超时通知继续使用现有单录音详情路由，不创建或查找批次页。

当服务器 Push 只包含 `recordingId` 时，客户端先通过持久批次索引查找 `batchId`：

1. 找到活动或保留批次时，按上述批次/单文件规则路由。
2. 找不到批次时，回退现有单录音详情路由。
3. 不允许因为缺少本地批次记录而丢弃服务器通知。

## 十、自动同步状态机

### 10.1 会话状态

| 状态 | 触发条件 | 可离开条件 |
|---|---|---|
| `waiting` | 未连接、正在录音、已有设备传输或前置权限未满足 | 条件恢复后重新规划 |
| `scanning` | 已连接、空闲、自动同步开启 | 获得完整目录快照或失败 |
| `planning` | 目录快照已冻结 | 候选清单持久化完成 |
| `transferring` | 至少一项正在同步 | 所有候选得到结果或被暂停 |
| `verifying` | 候选传输完成 | 文件、大小、哈希和本地记录校验完成 |
| `committing` | 本轮冻结候选全部通过 | 原子写入检查点 |
| `completed` | 检查点提交成功或确认没有新候选 | 新连接或新目录事件 |
| `paused` | 用户暂停 | 用户继续 |
| `failed` | 扫描、持久化或本轮同步出现不可继续错误 | 条件恢复后的新触发事件，或显式重试 |

“等待原因”作为字段保存，不扩展成多个状态：

- `deviceDisconnected`。
- `deviceRecording`。
- `otherTransferActive`。
- `permissionRequired`。
- `networkRequired`。
- `storageInsufficient`。
- `accountScopeChanged`。

### 10.2 单次运行算法

1. 验证账号作用域和已授权的完整 SN；缺少稳定 SN 时不得提交永久检查点。
2. 确认录音卡已连接、当前未录音且没有冲突传输。
3. 连续读取并确认目录，生成排序后的快照哈希。
4. 先合入旧的 `queued`、恢复后的 `syncing` 和达到 `next_retry_at` 的 `transient failed` 项；`permanent failed` 不得自动加入。
5. 再加入账本中从未出现的源签名。
6. `localDeleted` 和 `legacyUnknown` 项默认跳过；只有用户手动同步才能重新入队。
7. 对候选逐项传输并在每一项校验完成后立即写 `synced`。
8. 传输结束后重新读取目录；如果出现新源签名，继续下一轮规划。
9. 当冻结候选全部为 `synced`，且没有未处理的新源签名时，进入 `committing`。
10. 原子更新 `last_successful_auto_sync_at`、设备时间水位和快照哈希。

### 10.3 首次连接

对于该账号和该 SN 摘要没有检查点、没有迁移标记的新设备：

- 当前快照中的全部文件进入候选。
- 每个文件先写 `queued`，再开始传输。
- 任一文件失败时不提交全局水位，但成功文件保留 `synced`。
- 下次连接只恢复未完成项目和可自动重试的临时失败项目；永久失败等待用户显式重试。

### 10.4 后续连接和时间水位

设备时间不能作为唯一事实，因为当前工程可能从 `yyyyMMddHHmmss` 文件名前缀推导时间。策略如下：

- `recordedAt > committedThroughRecordedAt` 的未见文件直接视为新文件。
- `recordedAt` 为空的文件按源签名去重，未见即同步。
- 时间回拨或早于水位但源签名未见的文件仍同步，避免漏传。
- 已有 `synced`、`localDeleted` 或明确删除记录的相同源签名不自动同步。
- 没有新候选时不创建同步进度卡，也不更新“最近成功同步时间”。

### 10.5 断点恢复

- 每个文件完成后立即持久化，不等待整个批次结束。
- 进程退出或设备断开时，`syncing` 在恢复加载时转回 `queued`。
- 本地临时文件只有通过现有安全路径、大小和哈希校验后才能转为 `synced`。
- 发现已存在完整本地文件时复用，不重复下载。
- 临时文件不完整时按现有传输能力续传；协议不支持续传时只重试该文件。
- 断连后不更新检查点；重连先处理旧队列，再发现新文件。
- 连接过程中 SN 变化时立即取消本轮计划，不能把 A 卡结果提交到 B 卡账本。

中断与失败必须严格区分：

- 蓝牙/Wi-Fi 断开、App 进程退出、账号作用域切换和系统暂停属于“执行被中断”，没有设备失败回执时回到 `queued`，不增加失败次数。
- 明确的临时错误，如链路忙、短暂网络错误或可重试协议错误，写 `failed + transient`。同一运行周期最多自动尝试 3 次，采用带抖动的递增退避；其他文件不被阻塞。
- 一个运行周期用尽 3 次后锁存该项失败，当前连接内不继续循环；下一次设备重连、用户刷新或条件恢复事件可以开启新的运行周期并重新入队。
- 明确的永久错误，如源文件不存在、格式/协议不支持、校验持续不一致或设备明确拒绝该传输，写 `failed + permanent`，只能由用户显式重试。显式重试前仍需重新验证文件和设备条件。
- 任一文件失败都不提交本轮全局水位；同批其他成功文件继续保持 `synced`，后续运行不会重复下载。

### 10.6 自动同步触发矩阵

自动同步协调器只响应下列客观事件，不使用无边界的周期轮询：

| 事件 | 必要条件 | 动作 |
|---|---|---|
| 录音卡由未连接变为已授权连接，或 A 卡直接换成 B 卡 | 自动同步开启、SN 可验证 | 恢复该账号与 SN 的旧队列；消费当前连接的成功目录修订 |
| 成功目录修订增加 | 目录读取和本地校验都成功 | 无论自动同步是否开启都写账本与 `last_directory_read_at`；仅开启时触发规划 |
| 录音卡由非 `idle` 变为 `idle` | 当前账号和 SN 未变化 | 先由目录状态机完成有限结算读取，再消费成功修订；协调器不抢先重复扫描 |
| 外部设备传输结束 | 本轮明确因 `otherTransferActive` 等待，或控制器已经锁存目录脏位 | 恢复一次等待计划；若传输链路已经完成目录校验，直接消费其修订；终态下的无关传输抖动不启动新会话 |
| 已连接时开启自动同步 | 当前录音和设备操作空闲 | 消费尚未规划的最新成功修订；没有新修订时执行一次真实读取 |
| App 首次前台激活或短暂 `inactive -> resumed` | 当前账号仍有效 | 控制器核对连接和设备信息；仅目录尚未加载或已失败时读取，不重复连接阶段已完成的目录读取 |
| App 经历 `paused/hidden/detached` 后真实回到前台 | 当前账号仍有效 | 控制器请求一次连接/目录对账；协调器只恢复持久任务并消费成功修订，不额外发第二次扫描 |
| 用户主动刷新卡内文件列表 | 本次物理读取成功 | 成功修订是唯一生产触发源；页面不再补发第二个刷新事件 |
| 网络、权限或存储条件恢复 | 存在完全匹配的等待原因 | 清除等待并探测一次；无关恢复事件忽略 |
| 用户显式重试、App 恢复、重新开启自动同步 | 存在客观前置等待或失败目录 | 每个新事件各接受一次有界探测；失败后只保留失败或等待事实，必须等待下一个外部事件，不能在同一事件上自激活 |

同一 `user_scope + card_sn_digest` 同时只允许一个协调器运行。短时间重复事件合并为一次规划；运行中收到新事件只记录 `replanRequested`，当前安全边界结束后再规划，不能并发读取、传输或提交两份水位。

以下变化明确不是自动同步的生产触发源：原生 `runtimeSnapshot.files` 被动变化、未验证的目录哈希变化、页面重建、列表排序/筛选、通知投影变化，以及协调器未处于 `otherTransferActive` 等待时出现的传输结束边沿。它们可以更新只读投影，但只有 `successfulFileRefreshRevision` 前进后才允许写目录观察账本并触发新规划。

状态优先级固定为：`账号/SN 变化或断连 > 录音非空闲 > 设备传输/删除/Wi-Fi 恢复 > 设备信息读取 > 目录读取 > 自动同步规划`。高优先级事实使低优先级异步结果失效；低优先级需求最多锁存一个待处理事实。网络、权限、空间等客观等待不能遮住断连、录音或外部传输；硬件条件恢复后重新规划一次，如果前置条件仍缺失，只保留对应等待原因，直到新的条件恢复事件到来。

前台连接对账同样遵守这个优先级，但不新增业务枚举状态：并发对账共享一个 Future，`refreshDirectory=true` 是可向上合并的强意图；每次原生连接查询同时捕获对账代次和设备操作代次。查询期间发生新的原生快照、断连、换卡、用户设备操作或传输抢占时，旧结果只能丢弃，不能先写入 `runtimeSnapshot`、不能把 controller 改回 `idle`，也不能触发旧卡目录读取。MethodChannel 查询只在端口快照修订未变化时静默更新缓存，最终可见投影仍由控制器验权后提交。连接查询明确失败时，当前目录进入一次 `failed` 并保留旧行，本次前台意图即告结束；它不会自行再查，只有用户重试、下一次真实前台恢复或新连接才可重新触发。

连接、断开、解绑和改名共用单调命令代次；设备信息、录音状态和目录读取共同捕获设备会话修订。新命令开始、断连或稳定身份变化都会使旧读取失效。失效结果统一作为“被新事实取代”静默丢弃，不投影为当前设备失败；若命令结束后仍是同一连接修订和同一稳定身份，则只锁存一次补读，断连或换卡绝不补读旧卡。原生桥接层自己的命令截止时间是设备调用的唯一超时边界，Flutter 不再用一个更短且不可取消的 `Future.timeout` 提前释放操作锁，避免迟到的原生成功在锁释放后反向改写状态。

### 10.7 卡内文件目录刷新状态机

目录刷新与自动同步会话是两套职责不同的状态，不能互相代替。目录只保留现有五态：

| 目录状态 | 进入条件 | 可见数据 | 退出边界 |
|---|---|---|---|
| `disconnected` | 当前没有已授权录音卡，或连接/SN 已失效 | 只读展示该账号与历史 SN 的最后成功 `present` 缓存 | 新连接完成授权后进入 `reading` |
| `reading` | 已接受一次物理目录读取 | 保留上一次成功快照，禁用卡端写操作 | 原生返回后进入 `verifying`；明确失败或取消进入 `failed`；所有权失效只丢弃旧结果，由更新的断连、连接或操作状态决定当前态 |
| `verifying` | 原生目录完整返回 | 仍保留旧快照，校验本地文件、大小、哈希和当前连接所有权 | 全部校验完成进入 `ready`；任一步失败进入 `failed` |
| `ready` | 当前连接修订、SN 和校验结果一致 | 展示本次成功快照，包括合法的空目录 | 新的有效刷新进入 `reading`；断连进入 `disconnected` |
| `failed` | 读取失败、校验失败、录音中断或用户取消 | 保留旧快照但只读，显示可恢复错误 | 用户重试、前台恢复或新连接接受一次新读取 |

只有 `reading -> verifying -> ready` 全链成功，才递增单调的 `successfulFileRefreshRevision`，写入目录完成时间，并把当前快照的文件投影为 `present`、本次未出现的历史项投影为 `unknown`。失败、取消、录音打断、账号/SN 变化和旧连接迟到结果都不递增修订、不更新时间、不把旧快照改成空目录。成功读到零文件则是有效 `ready`：提交空快照，历史项保留为 `unknown`，离线当前目录不再显示它们。

为避免增加业务状态，刷新调度只保留四类最小锁存：

| 刷新意图 | 锁存方式 | 消费边界 |
|---|---|---|
| 新连接初读 | 单调 `connectionRevision`、该修订的已尝试标记和一个延后修订 | 只有真正加入物理读取或共享 drain 后才标记已尝试；设备信息读取或普通忙态只延后，不提前消费。每个新连接修订最多自动接受一次；失败后同一连接不自动循环，用户刷新或新的前台恢复可以再试 |
| 录音完成结算 | 一个 `requested` 位和一个进行中的有限结算 Future | 空闲且无设备占用时启动；结算所有权只绑定连接修订和稳定卡身份，同卡改名/绑定读取等命令只延后读取而不能消费意图；旅程进行中再次完成只增加一个尾随旅程，断连或换卡直接作废旧卡意图 |
| 真实前台恢复 | 前台协调器和控制器各一个可向上合并布尔位 | 外层任务只有在仍拥有当前前台代次并成功返回后才清除；控制器若因录音或传输延后，则由内层位接管并在条件释放后只补读一次 |
| 读取期间新增目录脏事实 | 一个待读取位和原因集合 | 当前读取已覆盖该事实则直接消费；否则当前读取结束后最多再读一次，不按事件数量累加 |

用户主动刷新不做持久锁存：按钮只在可立即执行时启用；请求一旦接受就共享当前目录 Future，成功或失败都结束这次用户动作。失败、取消和所有权失效不会被重新包装成新的刷新事件。

上述延后意图只共用一个控制器持有的零时延调度器，不为每个事件创建独立任务。录音、传输、设备命令或当前读取释放时可以重复请求唤醒，但都合并为下一次调度；回调开始前先释放自己的调度锁，再逐项检查客观边界。控制器销毁会取消该调度器，任何尾随刷新都不得跨越控制器或页面生命周期。

设备操作只保留两个布尔真值，不再增加状态：`hasActiveTransfer` 表示仍有未终结传输责任，用于禁止录音、卡端写操作和另一轮自动同步；`hasRunningTransfer` 表示此刻确实占用 BLE/Wi-Fi，用于阻止设备信息与目录读取。私有传输锁、正在执行的 Wi-Fi 阶段或 BLE 恢复均属于后者；已经完成 BLE 恢复的 `paused` Wi-Fi 批次只属于前者，因此允许只读刷新，但仍禁止新传输、删除和录音。任何时候最多存在一个设备信息读取或目录读取；同一连接的并发刷新共享当前 Future，不能发两条原生命令。

#### 10.7.1 物理目录读取触发矩阵

| 触发事实 | 是否物理读取 | 次数和锁存边界 |
|---|---|---|
| 新授权连接或直接换卡 | 是 | 每个连接修订一次；若正在录音或设备繁忙，锁存到首次空闲，不按页面数量重复。A 卡读取尚未返回时直接切到 B，B 按连接修订获得一个尾随读取；A 迟到结果只能丢弃 |
| 同一连接进入/返回页面、Widget 重建、排序、筛选、通知点击 | 否 | 只消费内存快照或账本投影 |
| 用户主动刷新 | 是 | 下拉、状态区按钮和操作菜单共用同一个 `manual` 请求；仅在“已连接 + 录音 `idle` + 无设备操作 + controller `idle/error`”时接受一次，否则明确拒绝，不排无界队列，也不显示虚假成功 |
| 录音由非 `idle` 变为 `idle` | 是 | 开启一个固件结算旅程，当前最多按 `350ms/900ms/1800ms` 读取三次；只有本次读取完整成功、修订前进且仍未发现新增文件，才进入下一档延迟。发现新增文件、读取失败、读取被拒绝或所有权失效均立即停止；重复完成事件只保留一个尾随旅程 |
| 录音完成时传输或 BLE 恢复仍占用设备 | 延后 | 目录脏位持续锁存；设备操作完整释放后消费一次，不能耗尽延迟窗口后静默丢失 |
| App 首次前台激活 | 视目录状态 | 先读取权威连接和设备信息；连接阶段已有成功目录时不重复读取，目录未加载或失败时读取一次 |
| 短暂 `inactive -> resumed` | 不因该事件强制读取 | 权限框、文档选择器等系统中断只恢复运行时并核对连接；已就绪目录不重读。若当前连接的初读原本尚未成功，则只继续那一个既有初读需求，不能把短暂中断另算成目录变化 |
| App 经历 `paused/hidden/detached` 后真实回到前台 | 是 | 每个真实恢复周期最多一次：先读取权威连接和设备信息；同一 SN 空闲后读取目录。后台可能完整经历录音，且固件可能只提供 MB 粒度或不提供存储量，因此不能仅靠容量差判断 |
| 真实回前台时传输或 BLE 恢复仍占用设备 | 延后 | 只锁存一个前台刷新位；该事件之后任何一次真实目录读取都会消费它，否则设备释放后补读一次。该次读取失败停在 `failed`，不自动循环 |
| 蓝牙单文件/批量同步 | 批次末最多一次 | 禁止逐文件读取；本地完成事实先直接投影，冻结批次结束后仅做一次一致性校验 |
| Wi-Fi 完成、暂停、失败、取消，或进程重启后发现已验证的暂存文件 | 最多一次 | 只有已经离开 BLE/切换热点时才先恢复同一录音卡；暂存文件证明上次已进入 Wi-Fi 阶段，幂等注册后也走相同恢复。恢复阶段继续持有设备操作权，批次不可关闭，成功恢复后读目录一次；尚未切换则不读取。恢复身份、令牌、连接或目录失败时保留本地完成事实并显式停在可重试错误，不伪装为空闲成功 |
| 卡内批量删除 | 批次末一次或零次 | 至少一条删除命令已发出、成功或结果不确定时读一次；全部在前置校验阶段被拒绝则不读取 |
| 本地删除、转写/纲要变化、通知更新、普通导航 | 否 | 只刷新本地库、账本、凭据和消息投影 |
| 已有目录读取进行中又出现客观脏事件 | 共享并最多尾随一次 | 录音完成、传输完成、卡内删除、新连接或真实前台恢复若发生在当前读取开始之后，按同一账号/SN 合并一个补读；连接原因必须同时比较连接修订，不能仅按原因名去重。当前读取已经由该事实启动则直接消费，不并发、不按事件数量累加 |

目录刷新成功后，UI 以 `successfulFileRefreshRevision` 是否前进判断本次请求是否成功，不能从旧 `ready` 推断成功。协调器也只消费这个修订：新修订可作为一次新鲜的传输前确认，不立即再扫一遍；只有实际尝试过传输才在末尾强制做一次校验读取。一次已接受的读取无论成功或失败都消费对应触发意图，失败停在 `failed` 等待下一次用户重试、真实前台恢复或新连接，绝不由状态机自激活。真实前台恢复任务若尚未启动、被短暂 `inactive` 取消、被新代次替换或执行失败，外层刷新意图不得被消费。失去代次或账号/SN 所有权的迟到结果不算新的失败事实，也不允许改写新状态。断连是硬边界：立即作废活动读取并清空尚未开始的尾随意图，原生迟到返回后仍保持 `disconnected`，不能再进入 `failed`。连接弹窗只取消自己发起且仍未结束的附近设备发现，绝不能从 controller 共用的 `scanning` 状态推断并取消文件目录读取。这样同时满足“该刷新必刷新”和“无客观变化不刷新”。

账号切换边界：

- 检测到活动账号与协调器 `user_scope` 不一致时，立即停止新的设备操作，当前 `syncing` 安全回写为 `queued`，本轮不得进入 `committing`。
- 切换账号只卸载内存投影，不删除原账号批次、文件账本、检查点和转写凭据。
- 新账号只加载自己的账本和通知；即使连接的是相同 SN，也不能复用前一账号的完成水位。
- 重新登录原账号后按原账号和 SN 恢复未完成队列；恢复前重新验证当前连接设备，不能沿用旧连接对象。
- 所有同步和转写通知都带账号/工作区作用域；非当前作用域的任务可以持久化更新，但不得显示在当前账号消息页或触发导航。

## 十一、本地删除和手动重新同步

### 11.1 删除本地文件

删除不能只执行物理文件删除后清理全部元数据。采用可恢复的两阶段流程：

1. 获取文件操作锁，阻止同一文件同时进入自动同步或上传。
2. 将账本从 `synced` 写为 `deleting` 并持久化。
3. 删除本地私有音频文件。
4. 删除本地录音库投影、播放位置，以及没有被活动批次、上传恢复或后端观察引用的草稿。
5. 将账本写为 `localDeleted`，保留卡 SN 摘要、源签名、文件名、时间、内容哈希和转写凭据。
6. 刷新本地录音列表和卡内文件页标签。

异常恢复：

- App 在步骤 2 后退出：恢复时检查文件；仍存在则回到 `synced`，已不存在则完成 `localDeleted`。
- 物理删除失败：回到 `synced` 并报告失败。
- 账本无法持久化：禁止继续删除，避免下次自动回流。

### 11.2 手动重新同步

用户在卡内文件页选择一个 `localDeleted` 文件并点击同步：

```text
card_state: deleted -> present（仅当前已验证目录中的显式选择）
localDeleted -> queued -> syncing -> synced
```

普通目录观察不能推翻设备已经确认的 `card_state = deleted` 回执。只有该源文件后来真实出现在当前 SN 的已验证目录中，并且用户明确选择它重新同步，才先确认 `card_state = present`；这样不会形成“本地已同步、卡内仍标记已删除”的矛盾组合。

同步完成后：

- 创建新的本地录音记录和新的 `local_recording_id`。
- 更新同一源签名账本，不创建重复的历史源文件记录。
- 更新文件级 `last_synced_at` 和全局 `last_transfer_completed_at`。
- 如果内容哈希与原记录一致，继续显示原有“已转写”标签。
- 如果内容哈希变化，视为新内容，不继承旧转写完成凭据。

### 11.3 删除卡内文件

卡内文件只能在卡内文件页删除：

- 必须连接正确 SN 的录音卡。
- 必须已经加载当前连接的有效文件目录。
- 录音卡正在录音或有冲突传输时禁止删除。
- 删除请求使用冻结文件身份，执行前再次核对目录修订和元数据。
- 只有设备明确返回成功后才写 `card_state = deleted`。
- 本地副本和转写凭据继续保留。
- 删除失败项继续显示并保留选中，成功项从当前卡内目录移除。

## 十二、升级兼容和多录音卡迁移

### 12.1 加法式数据库迁移

- 提升本地数据库 schema 版本，只新增表、列和索引。
- 迁移前保留现有数据库快照机制。
- 不重建、不清空 `local_recordings`、下载 manifest、上传草稿和传输任务。
- 迁移必须幂等；被中断后再次启动可以继续。
- 迁移完成标记按账号保存，不能用一个全局标记覆盖所有账号。

### 12.2 老版本数据播种

对于升级前已有录音卡使用记录的账号：

1. 从 `recording_card_downloaded_manifest` 播种已校验的 `synced` 文件。
2. 从 `local_transfer_records` 播种未完成和失败的同步任务。
3. 当前设备连接后，用当前完整 SN 将旧 `safeDeviceFingerprint` 历史归并到对应 SN 摘要。
4. 已有明确本地文件的记录继续显示“已同步”。
5. 无法证明同步历史的旧卡内文件标记为 `legacyUnknown`，在卡内文件页展示，但不在升级后的首次连接中自动全量回灌。
6. 用户可以显式选择 `legacyUnknown` 文件进行同步。
7. 没有任何旧连接、manifest 或传输任务证据的新账号/新录音卡，执行首次全量同步。

### 12.3 多录音卡保留

- 一个账号允许保留多张历史卡的账本，即使后端同一时间只允许一个活动绑定。
- 绑定 B 卡不删除 A 卡账本。
- 重新绑定 A 卡时按 A 卡 SN 摘要恢复历史水位、文件状态和转写标签。
- 账号退出登录先停止该作用域的新同步、上传观察和页面通知投影，将可恢复执行状态持久化后再卸载内存；不删除数据库记录，也不取消已经被后端接受的转写任务。
- 账号数据清除或 App 卸载才删除对应本地账本。

## 十三、并发、幂等与恢复约束

- 批量转写上传并发上限建议为 2，避免多个大文件同时占满网络和文件哈希资源。
- 自动蓝牙同步沿用串行文件传输；Wi-Fi 使用现有批次控制器，不另建第二套传输协议。
- 同一文件同时只能持有一个本地文件操作锁：同步、删除和上传互斥。
- 转写任务的 `jobId` 和后端幂等键继续由稳定本地录音身份产生。
- 批次控制器只负责编排和投影，不直接修改后端录音状态。
- 服务器接受录音后，App 退出不取消后端任务；下次启动通过上传草稿、批次记录和处理追踪器恢复。
- 单选和多选必须复用同一逐文件幂等提交器；多文件批次只是编排层，不能绕过原有 `jobId`、录音 ID 和后端重试边界。
- 自动同步完成与自动转写完成解耦。文件校验完成即可提交同步水位，不等待云端转写和纲要。
- 任何终态变化必须来自持久化成功、设备明确回执或后端权威事实，不能由 UI 计时器模拟成功。

## 十六、重点验收场景

### 16.1 批量管理

- 批量管理入口位于“录音文件”同一行最右侧，顶栏不再显示管理按钮。
- 全选、清除、退出和返回行为一致且不误选新加入文件。
- 本地页只能删除本地；卡内页只能删除卡内。
- 删除失败项保留，成功项刷新正确。
- 卡内文件页沿用现有 V3 操作面板与批量底栏，具备批量管理、全选、清除、退出、蓝牙传输、Wi-Fi 传输、卡内删除和主动刷新。
- 本地录音页不再出现读取卡文件、蓝牙/Wi-Fi 传输和删除卡内文件入口。
- 卡内目录读取失败或离线时保留上次成功快照，只有成功读到零文件才显示空列表。

### 16.2 批量转写

- 选择 1 个文件时不创建 `batchId` 和聚合消息，完全进入现有单文件链路。
- 选择 2 个文件时进入多文件链路；即使分类后只有 1 个需要处理，也不得退回单文件页面。
- 选择 5 个文件，其中 1 个已转写、1 个已有任务、3 个新文件，只新建 3 个远端录音。
- 旧文件已有远端录音但没有本地凭据时先按需查询；已完成则补写凭据，离线则等待核验，两种情况都不重复创建录音。
- 消息中心只有 1 条批次处理中消息。
- 中间页同时展示 5 行，完成项、处理中项、失败项和超时项互不影响。
- 首项完成时中间页继续保留并显示“查看结果”，不自动跳转；批次结果页默认展示锁存的首项摘要。
- “转写完成”和“资产已生成”只产生一条单文件结果消息；批次活跃时点击回到中间页定位该文件，批次终结后点击进入对应资产。
- 所有文件成功或跳过后聚合处理中消息结束。
- 有失败或超时时批次进入 `completedWithIssues` 并保留重试入口。
- App 重启后批次、计数、首项和每个文件状态一致。
- 24 小时截止到达但网络离线时不直接判超时；联网后权威查询仍未终结才进入本地 `timedOut`。
- 迟到的后端成功可以把本地超时更新为完成，但不会重复生成远端录音。

### 16.3 同步账本

- 新账号首次连接新卡自动同步全部文件。
- 第二次连接没有新文件时不创建同步卡片，不修改最近成功同步时间。
- 新增文件只同步新文件。
- 同步一半断连时不提交水位，重连跳过已经校验完成的文件并继续剩余文件。
- 断连和进程退出回到 `queued` 且不增加失败次数；临时错误按单次运行最多 3 次退避重试，永久错误只允许显式重试。
- 文件时间缺失、回拨或早于水位但身份未见时仍能同步。
- 用户删除本地文件后卡内页显示“本地已删除”，重连不会自动下载。
- 用户手动同步同一文件后重新显示“已同步”。
- 内容哈希未变化时保留“已转写”，内容变化时不继承旧标记。
- 解绑 A 卡、绑定 B 卡后 A 卡账本仍存在；重新绑定 A 卡恢复原状态。
- 账号切换后相同 SN 不共享本地账本。
- 已连接时开启自动同步、录音结束、冲突传输结束、用户刷新和等待条件恢复都按触发矩阵重新规划；重复事件不能创建并发同步会话。
- 初次前台激活和短暂系统 `inactive` 不重复扫描已就绪目录；真实后台恢复即使容量字段不变或缺失也只读取一次，撞上设备传输时在释放后补读一次。
- 录音结算等待期间执行同卡改名或绑定读取不能吞掉强制刷新；断连或换卡后旧卡结算不得读取新卡目录。
- 新连接初读撞上设备信息读取或普通忙态时只延后一次；A 卡初读未结束直接切 B 时，B 必须尾随一次，A 的迟到结果不得提交。
- A 读、B 尾随之后发生断连时，必须清空 B 的未执行尾随并保持 `disconnected`；连接弹窗关闭不得取消已经开始的卡目录读取。
- 暂停的 Wi-Fi 批次允许只读目录刷新，但在批次继续、取消或终结前仍禁止新传输、卡内删除和录音。
- 同步或转写进行中切换账号时停止旧作用域的新设备操作和导航投影，持久化可恢复状态；重新登录原账号后再验证设备并恢复。

### 16.4 升级和数据安全

- 老数据库升级后本地录音、已下载 manifest、未完成任务和上传草稿仍存在。
- 已知旧文件正确播种为“已同步”。
- 无法证明历史的文件显示但不会在升级后自动批量回灌。
- 重复执行迁移不会重复记录或覆盖较新的状态。
- App 更新保留账本；卸载 App 后本地账本和本地录音一起删除。

- 不修改 ASR 提供商协议。
- 不修改后端录音、云端笔记和纲要的权威状态定义。

## 十九、2026-09-05 运行态与传输缺口补充

### 19.1 “我的”页录音卡卡片不是页面计时器

录音卡运行时由应用级常驻 `RecordingCardController` 持有，页面只订阅快照，不能在
`initState`、返回、重进页面或滚动重建时创建或重置录音状态。硬件开始、暂停、继续和结束
事件更新同一份运行时；`0x0F` 这类没有稳定状态载荷的通知只作为“状态已失效”触发器，
随后合并为一次权威录音状态读取，读取进行中最多锁存一个尾随读取。

进行中录音优先从合法的设备文件名时间前缀 `yyyyMMddHHmmss` 恢复开始锚点；没有可信
前缀时才以首次权威观察时间兜底。这样晚进入页面和从后台恢复不会从零重新计时。断开、
连接错误或换卡是硬边界，立即投影 `idle`、归零耗时并清除旧观察，迟到事件不得恢复旧卡
录音状态。

卡片显示优先级固定为：

1. 蓝牙不可用、已断开或连接异常；
2. 录音中或已暂停；
3. 蓝牙/Wi-Fi 文件传输中；
4. 已连接。

页面前后台不改变该优先级。Android 的进程内后台监听在 operational connection 建立后开启，
断开或协调器销毁时关闭；它不宣称支持进程被系统杀死后的持续计时，重新启动后仍通过设备
文件名与权威读取恢复。

### 19.2 卡内文件交互所有权与删除规则

卡内文件页必须独占自己的批量 UI controller。其他录音列表的初始化、退出或销毁不能修改
本页的 `batchMode`，从而消除“点击批量管理后立即退出”。全选、清除、退出、行选择、批量
传输和批量删除全部使用同一个页面所有者。

单行三点菜单中的“蓝牙传输”和“Wi-Fi 传输”不再受“是否显示详情”控制：`本地已删除`
允许重新传输；`已同步`禁用重复传输，但仍允许删除卡内原文件。删除成功只把卡端存在状态
更新为已删除，本地录音、同步事实与转写事实继续保留。所有卡端修改都同时要求：当前连接
可操作、SN 摘要已验证、录音为空闲、没有活动传输。

同步卡片“开始”始终调用现有自动同步开关的启用边界。该动作会解除暂停并以当前已验证
目录重新规划，不能仅对旧的可恢复任务调用 `resume()`；没有旧任务时也必须能够创建新的
蓝牙下载队列。

### 19.3 文件目录刷新触发边界

就绪列表只保留标题栏紧邻三点菜单的刷新按钮和下拉刷新，不再单独占一行。以下客观事实
必须触发或锁存一次刷新：新连接、真实后台恢复、录音结束、传输完成和卡内删除成功。用户
主动刷新及错误态重试只在当下可读取时接受；忙时按钮、下拉入口禁用或明确拒绝，不额外排队。
客观必刷事件遇到录音、传输或已有读取时，才为同一连接代次合并一个尾随刷新；断开、换卡、
账号/SN 所有权变化会清除旧尾随意图。

普通页面重建、前后台 `inactive` 抖动、选择变化、滚动、计时刷新、相同运行快照和没有新增
文件的自动同步规划都不触发目录读取。只有成功目录读取可以推进成功刷新修订；失败保留旧
快照并等待显式重试或下一个客观触发。

### 19.4 传输进度、预计时间与发热治理

蓝牙单文件、自动同步、Wi-Fi 批次、Wi-Fi 引导弹层和云端录音对象上传统一展示可验证事实：
已传字节/总字节、当前吞吐和预计剩余时间。预计时间只在总量已知且速率为正的活动传输中
显示；暂停、失败、完成和服务端 ASR/纲要阶段不伪造倒计时。Wi-Fi 批次 ETA 使用批次剩余
总字节计算，不能把当前单文件 ETA 当成整个批次 ETA。

Wi-Fi 原生桥接以阶段变化、终态或最多每 250ms 一次的紧凑进度事件更新 Flutter，不再每个
数据块同时发送紧凑事件和包含完整文件目录的运行时快照。Flutter 对相同进度去重，协调器
已经发布状态时不再重复 `notifyListeners()`。

Android 流式解码器使用可复用的增长缓冲区和读写游标，socket 直接提交有效读取长度，消除
每块 `copyOf` 与累计 `pending += bytes` 导致的二次方复制。iOS 在 `Data` 上先校验固定头、
长度和完整性，只有完整帧通过校验后才物化 payload，避免为待续帧和坏帧提前分配。上述优化
不改变 CRC、64 MiB 上限、序列连续性、文件哈希或入库事务边界。

### 19.5 本轮额外验收

- 录音开始后先进入其他页面再返回，卡片状态与耗时不归零；暂停、继续和停止立即投影。
- 后台收到录音状态变化后，回前台无需等待轮询即可看到权威状态；断连后不保留“录音中”。
- 卡内页进入批量管理后保持选择态，直至用户退出、返回或动作被接受。
- 已同步文件可删除卡内原件；本地已删除文件可重新选择蓝牙或 Wi-Fi 传输。
- 无旧队列时点击同步卡片“开始”会创建并执行蓝牙同步任务。
- 目录就绪态只有紧凑刷新入口；忙态的必需刷新在释放后只补一次。
- 所有活动字节传输显示数量、速率和 ETA；服务端转写阶段不显示虚假 ETA。
- Wi-Fi 连续传输期间不再按 100ms 序列化完整目录，Android 解码内存增长保持线性。

## 二十、2026-09-05 最终收口与触发矩阵

### 20.1 运行态事实与页面生命周期彻底分离

“我的”页录音卡卡片、录音卡控制页和其他入口只读取应用级常驻控制器，不再把页面创建、
返回或重建当成录音开始条件。硬件录音通知触发权威状态读取；相同连接会话中的重复失效通知
合并，读取失败只按 `0 / 250ms / 1s` 做有限重试，断连、换卡或控制器销毁立即终止旧会话
重试。权威录音状态优先采用设备当前文件名中的 `yyyyMMddHHmmss` 作为开始锚点，没有可信
文件名时才用首次观察时间。页面恢复时根据锚点重新计算耗时，因此后台期间不依赖 Flutter
页面计时器持续运行，也不会因返回页面从零开始。

卡片状态优先级锁定为：蓝牙不可用/连接异常 > 录音中/暂停 > 文件传输中 > 已连接。文件
传输不能覆盖更重要的录音事实；断连必须清除旧录音锚点、旧传输进度和旧卡目录。

### 20.2 目录刷新的唯一触发矩阵

| 客观事件 | 行为 | 成功/失败边界 |
|---|---|---|
| 新连接且 SN 所有权稳定 | 读取一次卡内目录 | 仅成功读取推进成功修订；失败保留旧快照 |
| 用户点击刷新或下拉刷新 | 当前连接空闲时立即读取 | 忙时入口禁用或拒绝，不创建手动尾随意图；若恰有同连接目录读取则只等待该 owner |
| 硬件录音结束 | 冻结结束前目录签名并启动结算读取 | 按有限延迟重试；全部失败后锁存明确 failure |
| 蓝牙/Wi-Fi 传输完成 | 全部本地提交和账本写入完成后读取 | 传输失败或取消不伪装为目录成功 |
| 卡内删除成功 | 删除回执和账本墓碑写入后读取 | 已同步本地文件和转写事实继续保留 |
| 真实后台恢复 | 先加入已有录音结算 owner，再校准连接和设备信息 | 已有 owner 负责目录时不重复扫描 |
| 页面重建、选择、滚动、秒表 tick、系统 `inactive` 抖动 | 不刷新 | 不改变任何目录修订 |
| 断连、换卡、账号/SN 变化 | 清除旧连接尾随意图 | 旧结果不得提交到新卡 |

`canRefreshFilesNow` 同时排除目录读取、设备信息读取、连接校准、录音结算和设备写操作。任意
同连接的在途目录 owner 都由调用方等待，而不是读取旧快照后提前返回。录音结算 owner 在
`reading` 状态发布前完成锁存，自动同步因此只能看到“等待结算”或明确的成功/失败，不存在
扫描已经开始但协调器误判为空闲的窗口。

### 20.3 批量选择与转写结算边界

本地录音页现在自持页面级批量 UI owner，标题行普通态为“录音文件 / 批量管理”，批量态为
“已选择 N 条 / 全选 / 清除 / 退出”。清除只清空选择；退出、顶栏返回和系统返回先清空并
退出批量态。底栏只提供“删除本地”和“转写”，不会泄漏蓝牙、Wi-Fi 或卡内删除动作。
转写以用户冻结后的原始去重选择数为分流边界：1 个沿用单文件任务与详情路由，2 个及以上
创建持久批次和聚合中间页；不能按“需要新上传”的子集重新降级。独白历史这类无需再次转写
的条目仍保留在多文件预检中，并复用已有 `alreadyCompleted -> skipped` 结算，不新增状态，
也不进入上传。全为独白历史时转写按钮不可用。预检、确认或导航期间的列表变化不能修改
已经冻结的候选。

搜索只改变可见行：全选只追加当前搜索结果，但已锁存且暂时隐藏的条目仍计入“已选择 N 条”、
清除和最终动作，刷新真正移除实体时才裁剪该选择。转写预检以及卡内蓝牙批量动作在第一次
点击的同步阶段即获取页面锁，锁持有期间禁用对应底栏动作，`finally` 负责释放，快速双击
不能创建第二个预览、批次或同步账本转换。

一个批次中的单项上传、转写、完成、失败和超时独立结算。任一单项失败只结束自身；仍有
活动 operation 时聚合状态保持 `transcribing`，最后一个 operation 结束后才统一进入完成或
失败终态。录音结束目录结算仍在进行时，自动同步保持客观等待；重试耗尽后必须显示明确
失败，不能永久停在等待态。

### 20.4 所有字节传输的进度事实

录音卡蓝牙单文件、自动同步、Wi-Fi 单项与批次、录音转写对象上传、音频导入、备注追加和
消息中心统一读取已有进度事实。单文件云上传严格按 `draftId/jobId` 取值；批量消息只聚合
仍处于 `submitting + uploading` 的单项，合计已传字节、总字节和速率，再以剩余总字节计算
ETA。任务进入服务端转写、资产生成、完成、失败或超时后立即清除传输指标，不把旧速率
带入非传输阶段。没有首个速率样本时显示准备/计算中语义，不伪造完成时间。

备注追加页按所选卡文件的 `localFileKey` 订阅常驻蓝牙进度，其他文件的迟到事件不会污染
当前页面。消息列表和浮动消息 Hub 复用同一投影；显式批次仍只保留一条聚合处理中消息，
单文件完成、失败和纲要终态继续独立通知。

并发独立上传以 `draftId` 保存活动草稿集合，单条流水线完成、失败或取消只移除自身；账号或
Workspace 所有权变化才清空整个旧作用域集合。消息投影逐个草稿生成处理中行，标量
`activeDraft/status` 仅保留为兼容与失败回退，因此批量任务或另一个独立上传更新前台标量时，
不会让仍在上传的兄弟任务从消息中心消失。纯浏览卡内文件时不订阅上传控制器，只有手动上传
展示或自动同步进入转写阶段后才按需建立该依赖。

### 20.5 Wi-Fi 发热优化边界

Android 与 iOS 的 CRC16/IBM 从逐字节 8 轮位运算改为一次性 256 项查表，协议多项式、初值、
字节序和校验结果不变。Android socket 使用复用读缓冲和读写游标解码，避免每个网络块复制
和累计缓冲的二次方增长；iOS 在完整性校验前使用 `Data` 切片，只在完整帧通过校验后物化
payload，不为待续帧或坏帧提前分配。
蓝牙与 Wi-Fi 进度事件最多每 250ms 发布一次，阶段变化和终态强制发布；数据块到达不再伴随
完整目录快照序列化。文件写入、SHA-256、序列连续性、长度上限和最终账本事务仍保持原有
权威边界。

这些修改消除了代码中可确认的高频计算、重复复制和过密平台通道刷新，但“手机发烫改善”
必须在实体录音卡、相同文件和相同网络条件下以真机温度/CPU 采样验收，模拟器测试不能代替
热性能结论。iOS 当前累计 `Data.append`、从头 `removeSubrange` 以及校验后 `Array -> Data`
所有权转换仍是大文件场景的残余分配风险；只有真机 Instruments 证明其占比显著时，才进入
读游标缓冲区和单一 payload 所有权的下一阶段优化，避免无证据地改动稳定协议路径。
