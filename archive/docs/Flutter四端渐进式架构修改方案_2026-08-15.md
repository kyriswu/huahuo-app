> 仓库：`Xieyangzai/Flutter-mobile`  
> 分支：`Flutter-Desk-Mobile`  
> 读取基线：`2a8c6f4b784364bf737a40f5ac536c8db8943ce6`  
> 最新提交：`fix(mobile): defer chat route state updates`  
> 方案日期：2026-08-15  
> 目标平台：iOS、Android、Windows、macOS

---

## 1. 方案目标

当前仓库已经同时存在移动端与桌面端 Flutter Application：

```text
Flutter/
├── src/                     # iOS + Android
├── desktop/                 # Windows + macOS
├── packages/
│   ├── huahuo_api/
│   ├── huahuo_editor/
│   └── huahuo_foundation/
├── scm/
└── pubspec.yaml
```

本次改造的目标不是把四个平台强行合并为一个 Application，也不是复制四份代码，而是在**不破坏现有功能、不改变现有产品行为**的前提下，将跨端重复的远程 API、公共 Contract、纯业务规则逐步下沉到共享层。

最终保持：

```text
                         Shared Packages
                ┌────────────────────────────┐
                │ huahuo_api                 │
                │ huahuo_editor              │
                │ huahuo_foundation          │
                │ [optional] huahuo_app_core │
                └─────────────┬──────────────┘
                              │
                 ┌────────────┴────────────┐
                 │                         │
         Flutter/src                 Flutter/desktop
        Mobile Application          Desktop Application
            │        │                  │        │
           iOS    Android             Windows   macOS
```

核心原则：

1. **一个仓库、一个 Flutter Workspace。**
2. **两个 App Shell：Mobile 与 Desktop。**
3. **四个平台构建产物。**
4. **共享 Remote/API/Contract，不强行共享平台 UI。**
5. **现有功能优先于目录“整洁”。**
6. **先兼容，后收敛；先新增共享实现，后删除重复实现。**
7. **每一步均可独立回滚。**

## 3. 与上一版方案相比的关键调整

上一版方案倾向于尽早新增：

```text
packages/huahuo_app_core
```

重新阅读当前最新代码后，建议调整为：

### 第一阶段：不立即建立大而全的 `huahuo_app_core`

先继续强化已经稳定存在的：

```text
huahuo_api
```

其职责限定为：

- API Transport；
- Endpoint Catalog；
- API Contract；
- 公共 DTO；
- 公共输入校验；
- Idempotency；
- Remote Domain Client；
- 与平台无关的 API 结果模型；
- 与平台无关的远程数据转换。

### 第二阶段：只有出现“至少两个平台都真正需要同一个应用状态机”时，再建立 `huahuo_app_core`

`huahuo_app_core` 必须是**按真实复用需求产生**，不能为了架构漂亮提前制造。

适合未来进入 `huahuo_app_core` 的内容：

- 完全相同的纯业务状态机；
- 完全相同的领域规则；
- 完全相同的跨平台 Use Case；
- 不依赖 Flutter Widget；
- 不依赖 MethodChannel；
- 不依赖 `flutter_secure_storage`；
- 不依赖 `path_provider`；
- 不依赖本地数据库的具体实现；
- 不依赖 Windows/macOS/iOS/Android 插件。

不适合进入 `huahuo_app_core` 的内容：

- Mobile `ChangeNotifier` 如果 Desktop 并不使用相同状态模型；
- Desktop Task Tracker；
- Chat Recovery Store 的本地实现；
- 图片磁盘 Cache；
- Mobile Router；
- Desktop Window State；
- 本地 SQLite DAO；
- Flutter Provider/Riverpod 装配；
- Native Bridge。

# 6. 本次重构的行为不变约束

所有重构 PR 必须同时满足以下约束。

## 6.1 API Contract 不变

不得因共享化修改：

- Endpoint ID；
- URL Path；
- Query 参数；
- Request Body；
- Header；
- Idempotency Key 语义；
- ETag / `If-Match`；
- 状态码处理；
- Response 字段解析；
- Streaming Event 语义；
- Error Code 映射。

## 6.2 Token 与 Session 不变

移动端现有：

```text
SecureTokenStore
SessionStore
```

桌面端现有：

```text
SecureDesktopTokenStore
```

第一阶段不统一实际持久化 Key，不迁移用户 Session 数据。

特别禁止：

```text
直接更换 Secure Storage key
直接统一 Mobile/Desktop token schema
直接删除旧 token key
```

否则已经登录的用户可能升级后全部退出。

## 6.3 Device ID 不变

不得因 Runtime 重构改变四个平台当前发送给服务端的 `deviceId`。

尤其 Desktop 目前仍使用：

```text
desktop-{hostname}
```

在没有正式设备身份迁移协议前不得偷偷替换。

## 6.4 本地缓存 Schema 不变

当前新增的大量功能依赖本地恢复：

- Chat recovery；
- Chat thread alias；
- Resource image cache；
- Topics cache；
- Workspace content sync；
- Daily topic cache；
- Pending messages；
- Recording state。

共享化时：

```text
缓存路径不变
缓存 key 不变
序列化字段不变
恢复顺序不变
过期策略不变
用户隔离 scope 不变
Workspace scope 不变
```

## 6.5 Chat 行为不变

当前 Chat 是整个仓库最敏感区域。

必须保留：

- pending message 行为；
- durable message 回读行为；
- server-confirmed cache；
- thread detail lag 合并；
- message ID 去重；
- legacy user turn reconciliation；
- assistant message 不做语义折叠；
- route re-entry 恢复；
- thread alias；
- run tracker；
- notification pending projection；
- chat route state 延迟更新；
- transcript flow；
- note creation；
- resource image cache。

因此前几个 PR **禁止搬迁 `ChatController`**。

## 6.6 Native Contract 不变

第一阶段禁止重构：

```text
Flutter/src/android/
Flutter/src/ios/
Flutter/desktop/windows/
Flutter/desktop/macos/
```

除明确修复平台 Bug 外。

尤其不得改变：

- MethodChannel 名称；
- Android Intent Contract；
- iOS Method Channel；
- Android 文件选择行为；
- iOS 文件选择行为；
- 录音桥；
- ASR Bridge；
- Home Widget；
- Push；
- Payment；
- Screen Capture；
- Manifest 权限；
- Info.plist 权限。

# 16. PR-7：评估是否需要 huahuo_app_core

# 25. 回滚策略

每个 PR 必须可以单独 revert。

```text
新增 shared client
+
删除全部旧 adapter
+
修改 storage schema
+
修改 UI
+
修改 native
```

推荐：

### 第一步

新增 Shared Implementation。

### 第二步

旧 Adapter 切换为调用 Shared Implementation。

### 第三步

稳定至少一个迭代周期。

### 第四步

单独 Cleanup PR 删除确认无用的重复逻辑。

任何线上异常可以：

```text
revert 最新 Adapter 切换 PR
```

而不需要恢复大量目录结构。

# 27. 最终结论

基于 `Flutter-Desk-Mobile` 当前最新代码，不应对现有工程进行一次性“大一统”重构。

当前仓库已经出现了正确的共享模式：

```text
huahuo_api Domain Client
        ↓
Mobile / Desktop Adapter
        ↓
Platform State / UI
```

接下来最安全的路线是：

> **保留现有两个 App Shell，保留现有 Controller/Port/Cache/Native Contract，先把 Remote Client 与 API Runtime 逐步共享。**

尤其当前 Chat、Pending Message、Transcript、Topics、Workspace Sync 和桌面 Recovery/Task Tracker 都处于近期快速演进状态，应该优先保护其既有行为，而不是为了提高代码复用率提前合并状态机。

推荐第一刀只做：

```text
Shared ApiClient Runtime / Builder
```

并保持：

```text
Mobile apiClientProvider
DesktopServices
```

的对外接口完全不变。

完成后再逐步迁移：

```text
Auth Remote
→ Assets / Workspace / BookWork
→ Chat Remote
→ 按真实重复度决定是否引入 huahuo_app_core
```

这套实施方式能够最大程度保证：

```text
现有功能不丢
线上用户不掉登录
本地缓存不失效
Chat 不回归
四端仍可独立演进
跨端重复代码持续下降
```

并且与当前仓库已经形成的架构方向保持一致。
